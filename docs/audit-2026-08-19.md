# IdrockBench — technical and editorial audit

**Date:** 2026-08-19 · **Scope:** `idrock-eval/`, `eval.idrock.uz/`, `DTM2019_public.csv`, `idrock-dtm2019-dataset.docx`
**Method:** full read of all 3,549 lines of harness code and all six datasets; every claim below was reproduced by executing the repo's own functions against the repo's own data. Externally, the audit compares against lm-evaluation-harness, HELM, lighteval, OpenCompass, HF Open LLM Leaderboard v2, LiveBench, ARC Prize, SWE-bench, and the peer benchmarks in this space (TUMLU, KazMMLU, TurkishMMLU, ArabicMMLU, Global-MMLU, INCLUDE, SEA-HELM, Belebele, FLORES-200).

---

## 1. Verdict

**The engineering is competent. The measurements are not currently valid, and the published leaderboard cannot be traced to any run.** Nothing here is unfixable, and the underlying assets — especially the DTM corpus — are genuinely good. But `eval.idrock.uz` is live right now, and four of its five score columns would not survive an outside reader spending an hour with the code.

Three facts define the risk:

1. **The MMLU-Pro column never showed the model the correct answer.** For 147 of 200 questions the gold answer is not among the options that were rendered into the prompt. Maximum achievable score ≈ 26%; published scores are 6.5–15.5%, i.e. noise around the 10% random baseline. It is not a hard benchmark — it is a broken one.
2. **The benchmark systematically penalises correct Uzbek.** Three independent scoring paths reward ASCII-typo Uzbek, or English, over correct Uzbek orthography. On `web_of_lies_v2`, a *perfect* Uzbek answer typed with the ordinary curly apostrophe (`yo’q`) scores **26.67%** — below a model that answers "ha" to every question (**30.0%**) — while a perfect answer in *English* scores **100%**. The lowest-ranked model on the site is the Uzbek-specialised one.
3. **20 of the 50 published score cells came from no run at all.** The entire IFEval column (all 10 models) has no source file anywhere in `results/`. Its values carry 3–4 decimal places that no code path in the repo can emit.

The good news: the repos are private, the held-out eval sets on HuggingFace are private, and the site has no inbound links yet. The exposure is contained and there is time to fix this properly.

## 3. What is broken, with evidence

Every number below was produced by running the repo's own code.

### 3.1 MMLU-Pro — the dataset is destroyed at load time

`benchmarks/mmlu_pro.py:50` — `_parse_options_string` splits on `\n`. But the CSV stores `options_uzb` as a **numpy array repr**, which only inserts newlines when the line exceeds ~75 characters. Short option lists collapse into one or two "options" carrying stray quote marks.

Parsed option counts across all 200 rows:

```
1 option  → 50 rows      4 options →  10        9 options →  4
2 options → 79 rows      5 options →   7       10 options → 22
3 options → 25 rows      8 options →   3
```

**147 / 200 rows (73.5%) have `answer_index >= len(parsed_options)`** — the correct answer is never rendered. Actual prompt the model receives (question_id 262, gold = D):

```
Savol: AlforsCompany 1974 yil 1 yanvarda $30,000 miqdoridagi ... yakuniy zaxira qancha bo'ladi?

A) $50,200' '$45,100' '$60,400' '$56,300' '$58,800' '$54,400' '$65,500
B) $62,900' '$48,700' '$52,600

Javob:
```

Compounding problems on the same column:

- **All 200 questions are from a single category (`business`).** The site and README describe MMLU-Pro as covering "STEM, humanities and social sciences." It is a 200-item business quiz.
- **The answer extractor is broken for Uzbek.** `re.search(r'\b([A-J])\b', ...)` takes the *first* standalone letter. The ASCII apostrophe is not a word character, so `to'g'ri` ("correct") tokenises to `TO`, `G`, `RI`. `"To'g'ri javob: H"` — the most natural Uzbek phrasing for "the correct answer is H" — extracts **G**. Same for `a'lo` → `A`, `e'lon` → `E`, `o'g'il` → `G`.
- **No `<think>` stripping.** `dtm.py` strips reasoning blocks; `mmlu_pro.py` does not. Reasoning models are scored on the first letter inside their scratchpad.
- **Rows 244–271 are machine-generated noise, not translation.** e.g. id 263 options: `'A q s.' 'O b h.' 'P m d.' 'P d k.'`; id 259 `question_uzb` = `"Bu nima"` (7 chars) for a 324-char English question.
- **The documented default doesn't run.** `default_dataset = "mmlu_uzbek.csv"` does not resolve from the repo root (the file is in `datasets/`), so it falls through to the HuggingFace loader and fails. The README's Quick Start command cannot work.

**Recommendation:** retract the column. Re-serialise the CSV as JSON arrays, assert `answer_index < len(options)` at load, delete or re-translate rows 244–271, expand beyond `business`, and adopt MMLU-Pro's official extractor. Until then, do not publish an "MMLU-Pro" number — the name sets an expectation the artifact doesn't meet.

### 3.2 The Uzbek-orthography penalty — the most damaging finding

Three separate scorers reward the wrong thing.

**Reasoning (`web_of_lies_v2`)** — measured over all 50 items with the real scorer:

| what the model answers | score |
|---|---|
| perfect Uzbek, ASCII apostrophe `yo'q` (U+0027) | 100.00% |
| perfect Uzbek, canonical `yoʻq` (U+02BB) | 100.00% |
| **perfect Uzbek, typographic `yo’q` (U+2019)** | **26.67%** |
| perfect answer in **English** (`yes, no, yes`) | 100.00% |
| constant guess `"ha, ha, ha"` | 30.00% |

`NO_WORDS` covers U+0027, U+02BB and a backtick but not the curly apostrophes that most models actually emit. And because `_score_web_of_lies` **left-aligns** short answer lists (`reasoning.py:238,269`), one unrecognised token shifts every remaining answer one slot and destroys the whole item rather than costing one slot.

**Translation** — the FLORES Uzbek references in `datasets/translation_benchmark.json` use ASCII `'` (480 occurrences) and canonical `ʻ` exactly once. A model that writes orthographically correct Uzbek is scored against typo references. Published sacreBLEU behaviour on this substitution alone is roughly 100 → 20 BLEU on affected segments.

**Zebra puzzles** — 11 of 100 items have apostrophes in the Uzbek gold; a perfect run scores 100% with ASCII and 91.6% with a curly apostrophe.

**Recommendation:** NFC-normalise and fold `{U+0027, U+2018, U+2019, U+02BC, U+0060, U+00B4} → U+02BB` on both the model output and every gold string / keyword / reference, everywhere, before any comparison. This is a ~20-line shared helper and it is the single highest-value fix in the repo.

### 3.3 DTM — the strongest track, undermined by extraction and keys

- **Up to 55% of responses yield no answer at all, and are silently scored 0 while `answered` reports 1000/1000.** From each run's own `predicted_distribution`:

  | model | in-range predictions | unextractable | published DTM |
  |---|---|---|---|
  | qwen3.5:9b | 450/1000 | **55.0%** | 36.9 |
  | qwen3.5:35b | 586/1000 | **41.4%** | 47.0 |
  | gemma4:26b | 807/1000 | 19.3% | 57.8 |
  | gemma4:e4b | 973/1000 | 2.7% | 52.5 |
  | mistral-small3.2:24b | 996/1000 | 0.4% | 40.8 |

  The DTM column currently ranks *extraction success* as much as knowledge.

- **`extract_answer` takes the LAST `\b[ABCD]\b` match.** `"Javob: B. A varianti noto'g'ri, C ham, D ham."` → `D`. And 103/1000 question texts already contain a bare A/B/C/D token from apostrophe splitting (`a'zolari` → `A`) or matching-exercise labels (`1-b`), biasing systematically toward A.
- **Only closed `<think>…</think>` blocks are stripped.** With `max_tokens=2048`, a truncated reasoning trace survives intact and a letter is scraped out of unfinished deliberation.
- **8 items have `answer: null`, and `dtm.py:48` invents option A as the gold** (`LETTER_TO_INDEX.get(letter, 0)`), then scores and counts them.
- **2 items have byte-identical options** (ids 191, 545) and the shuffle remaps gold by *text*, so a correct reader has a coin-flip chance of being marked wrong.
- **Two answer keys in the held-out set appear wrong** (ids 855, 856 — the Moon free-fall pair), plus two in the public release (qids 748, 780). These were derived in closed form and cross-validated against sibling items during review; **please have a physics teacher confirm before acting.** The technique — solving near-duplicate item pairs and checking key consistency — found 4 errors in ~20 pairs and is worth running over the whole physics and maths sections.
- **2 of the 1,000 held-out items also appear in the public 2,066-item release** (same question, permuted options). Small, but it contradicts the paper's disjointness claim.
- The paper's "correct-answer labels balanced uniformly" is C260/A252/D244/B236 + 8 nulls (statistically fine, χ²=1.29, but not the stated exactness), and "topics sampled uniformly within each subject" is false for tarix (12–34 per topic) and fizika (3–10).

### 3.4 IFEval — the wired-in implementation measures English, and has a 20.7% floor

- **`benchmarks/ifeval.py:218` returns `question["prompt"]` — the English original.** The Uzbek dataset ships `prompt_uz` on all 541 rows; the wired runner never reads it. There is no path in the repo or the README that evaluates Uzbek IFEval prompts.
- **A model that replies `"Salom! Bu javob."` to all 541 prompts scores 20.7% strict accuracy.** Measured with each row's real kwargs. Two published IFEval scores (qwen3.5:9b 17.65, qwen3.5:35b 20.225) are *at or below* that floor.
- Even the good standalone runner (`benchmark_ifeval_uz.py`) has a **14.8%** floor, because the constraints themselves weren't localised.
- **The kwargs are English while the prompts are Uzbek.** The prompt asks for «mushuk» and «taqillatish»; the checker looks for `cat` and `knock`. Measured coverage: `end_phrase` 1/26 localised, `section_spliter` 0/14, `first_word` 3/12, `keywords` 44/86, `forbidden_words` 58/117. So `keywords:existence` is unsatisfiable for half the rows and `forbidden_words` is trivially satisfied for the other half — the per-instruction table measures translation coverage, not instruction-following.
- `constrained_response` requires the English phrase "my answer is yes." while the prompt demands "Mening javobim ha." → 10/10 unsatisfiable. `repeat_prompt` → 41/41 unsatisfiable.
- The better implementation, `benchmark_ifeval_uz.py`, is **not wired into `run_benchmarks.py`** — and it scores a failed API call as an empty response, which *raises* the score toward the 20.7% floor rather than lowering it.

### 3.5 Translation — wrong aggregation, wrong metric name, half the advertised scope

- **`extract_answer` keeps only the first line of the response.** A model that writes `"Mana tarjima:\n<translation>"` scores BLEU 0.0. This is the direct cause of the published `qwen3.5 translation = 0.0`, which is currently on the site as if it were a measurement of translation ability.
- **Sentence-level BLEU averaged over items, not corpus BLEU.** Not comparable to any published number; sacreBLEU signatures are never recorded.
- **`sentence_chrf` is chrF, not chrF++** (`word_order=2` is required). The site, the README and the benchmark card all say chrF++.
- **Russian is never evaluated.** All 200 rows carry `text_ru`, `DIRECTION_PROMPTS` defines `uz_ru`/`ru_uz`, the site advertises "Tarjima uz↔ru↔en" — but the loader only fans out `uz_en` and `en_uz`. Every run shows `total_questions: 400` = 200 × 2. The README additionally claims `uz_tr`/`tr_uz`, which exist nowhere.
- The headline number is a micro-average of chrF pooled across two different target languages, then averaged into `overall` alongside accuracy percentages.

### 3.6 Reasoning — contradictory prompts, dead parse paths, retired items

- **The harness prepends "don't show your reasoning steps" to a reasoning benchmark.** 119 of 200 Uzbek prompts themselves say *"Bosqichma-bosqich o'ylang"* (think step by step). Every item ships two contradictory instructions, and instruction-following-strong models are punished hardest.
- **The primary `<solution>` parse path is dead for 150/200 items.** Only 50 of 100 zebra prompts retained the tag through translation; spatial and web_of_lies never had it. Three quarters of the set is scored by fallbacks.
- **Those fallbacks award credit they shouldn't.** `gt_word in llm_word` substring matching gives full credit for `"1 emas, kinorejissyorlik emas, …"` (every slot explicitly negated) and for answering `10` where gold is `1`. The spatial scorer accepts any of the last three bold spans, so hedging with three candidates triples the hit rate.
- **22 of 100 zebra items still have the English string as their Uzbek gold** — models answering in Uzbek are scored against English answers.
- **100 of 200 items carry a `livebench_removal_date`** (zebra 2024-11-25, web_of_lies_v2 2025-04-02). LiveBench formally retired them; we are still scoring them in 2026 and no code reads that field.
- The reported "accuracy" is a partial-credit score with a ~15.6% floor for a constant responder — then averaged 1:1 with 0-baseline accuracies into `overall`.

### 3.7 The leaderboard and the publishing pipeline

- **20/50 cells have no source run.** The whole IFEval column (10/10 models), plus translation/DTM for deepseek-r1, alloma, llama3.1:70b, llama3.1:8b, gpt-oss:20b.
- **`gemma4:e4b` DTM shows 39.8; the run says 52.5. 39.8 is that run's `overall`.** A copy-paste.
- **The file is hand-edited** — `"dtm":39.8, ` with no space and trailing whitespace, a blank line inside the array, and 3–4 decimal places that `round(x, 1)` cannot produce.
- **`export_results.py` can never retract anything.** It seeds from the existing `results.json` and only `.update()`s, so a deleted benchmark or a deleted model keeps its published value forever. Its default output path (`idrock-eval/results.json`) isn't even the file the site serves — which is *why* hand-editing became the publishing mechanism.
- **The alloma row was manually renamed** from `kmamaroziqov/alloma-8b-q4` / org `Unknown` to `alloma-8b-q4` / org `Uzbek LLM Lab`. Re-running the exporter today publishes the model **twice**, under both identities, with different scores and different OS badges.
- **"Overall" averages over whatever subset each model happens to have** (`script.js:249`) — and the harness computes a *different* "overall" under the same name. Medals are assigned after sorting and after filtering, so one click on any column header hands 🥇 to the worst model; `deepseek-r1:32b` (the one with DTM = 4.7) takes gold on the first ascending click. Typing in the search box re-medals too.
- **`answered` is dropped at publish time.** `gemma4:26b`'s gold-medal reasoning score of 55.38 rests on 120 of 200 items; a reader cannot learn that.
- No n, no confidence intervals, no random baseline, no run date rendered (three conflicting `lastUpdated` values exist, none is displayed), no methodology page, no per-model detail, no LICENSE, no CITATION, and all three GitHub links point at the org rather than a repo.

### 3.8 Reproducibility and engineering hygiene

- **Nothing records what was run.** Result files carry only `scores, details, model, organization, provider, timestamp, temperature`. No dataset source, no dataset hash, no split, no `max_samples`, no `max_tokens`, no `--no-think`, no seed, no harness commit, no quantisation. Since `mmlu_pro`'s default doesn't resolve and `translation` has no default at all, every published number required undocumented CLI flags that appear nowhere.
- **`--no-think` and per-benchmark `max_tokens` (4096/4096/2048/2048/512) are invisible in the output**, so a thinking-enabled and thinking-disabled run of the same model are indistinguishable.
- **Ollama quantisation is unrecorded.** `deepseek-r1:32b` is a Qwen distill at Q4_K_M, published as "DeepSeek-R1 32B / DeepSeek". `alloma-8b-q4` is 4-bit and compared against fp16 models with no note.
- **A failure in benchmark 4 of 5 discards benchmarks 1–3.** The single `json.dump` is after the loop, and `translation` has no default dataset — so the README's own default command dies at benchmark 4 and throws away hours of completed work. This is why the committed result files hold 2 of 5 benchmarks.
- **API errors and truncations are scored 0.0** in every benchmark, mixing infrastructure failure into model quality.
- **No retries, no backoff, no concurrency, no caching, no resume** in the main runner — plus a hardcoded `time.sleep(0.5)` per item.
- **Per-item records are thrown away.** Only aggregates are saved; raw responses go to gitignored free-form `.log` files (and IFEval writes none). Correcting any extraction bug therefore requires re-running 10 models × ~1,940 items, and historical numbers can never be reconciled.
- **`.gitignore:1` is `test_*`**, which matches at any depth — anyone writing tests will `git add tests/` and silently commit nothing. There are no tests, no CI, no LICENSE, no CITATION.cff.
- `requirements.txt` is missing `langdetect`, `python-dotenv`, `orjson`, `google-genai` — so `benchmark_ifeval_uz.py` doesn't import, and `langdetect` failing silently makes all 31 language checks pass.

## 4. What is genuinely good

Worth saying plainly, because the fixes should build on this rather than restart:

- **The DTM corpus is a real asset.** 3,066 natively-authored Uzbek items from national exam material, VLM-extracted with figure-dependent items excluded, LaTeX preserved, `<u>` markup preserved for grammar items, LLM-assisted per-item cleaning, and a genuinely stratified 1,000-item held-out subset. Verified clean: 0 malformed LaTeX, 0 unbalanced `<u>`, 0 mojibake, 0 items depending on an absent figure, 0 empty options. That is better hygiene than most of the peer benchmarks.
- **`benchmark_ifeval_uz.py` is a faithful port of the official IFEval checkers**, including the correct 8-variant loose protocol, resume state, and per-instruction-type breakdown. It just isn't wired in.
- **The DTM option-shuffling for positional-bias mitigation** is the right instinct and ahead of most peers.
- **The site is well built** — clean i18n, a real cache-busting build step, and a submission flow where the Telegram token correctly stays server-side and RLS is enabled with no policies. The security model of the edge function is sound; what it lacks is throttling and a privacy notice.
- **The data-descriptor draft is close to submittable** and the IEEE DataPort DOI is already minted.

## 5. Where this sits against the field

The comparison set matters, because it sets the bar and also shows how low some parts of it are.

- **TUMLU** (ACL 2025 Long) already covers **Uzbek** — 8 Turkic languages, ~700 verified Uzbek items from university-entrance material, CC BY 4.0. Claude 3.5 Sonnet scores 68.6–69.1% on Uzbek, the lowest of all nine languages. **This is the direct comparison and it must be cited.** Idrock's advantage is scale (3,066 vs ~700 for Uzbek) and subject breadth.
- **`murodbek/MMLU-uz`** is 14,257 machine-translated items whose card explicitly says it has had no human review. Running the same models on native IdrockBench-DTM vs MMLU-uz and publishing the divergence would be a strong, cheap result.
- **`tahrirchi/uzlib`** — 1,861 Uzbek linguistics MCQs, MIT. Complementary, not competing; cite it.
- **KazMMLU** (ACL 2025 Long) is the regional precedent: national exam corpus → ACL long paper. Their entire validation section is "two professional annotators manually reviewed all questions." **No Turkic-language benchmark reports an inter-annotator agreement statistic.** ArabicMMLU got into ACL Findings on "100 questions, 2 verifiers, 96% match."
- **The cheapest credibility win available:** report a real Cohen's κ or Krippendorff's α on a stated sample with ≥3 independent annotators and a written adjudication rule. That alone puts IdrockBench ahead of TUMLU, KazMMLU, TurkishMMLU and ArabicMMLU on validation rigour.
- **Second cheapest:** a contamination analysis. KazMMLU, ArabicMMLU and TUMLU have none. Because the DTM source is 2019 scanned print, a *low* contamination number is a headline result, not a footnote.
- **Third:** a culturally-grounded subset with published counts, following Global-MMLU's CS/CA split — then show that model rankings reorder between the two.

## 6. Recommended target state

### 6.1 Harness

Two viable routes.

**Route A (recommended): define the tasks in `lm-evaluation-harness`.** You get, for free, everything §3.8 lists as missing: task versioning with a changelog, YAML task inheritance, named filter pipelines for answer extraction, `acc_stderr` on every metric, per-sample output dumps, caching and resume, chat-template handling, and backends for OpenAI/Anthropic/vLLM/Ollama. It is also a distribution multiplier — Global-MMLU ships an official task there, and KyrgyzLLM-Bench explicitly integrated into existing frameworks for reach. Keep the bespoke Uzbek scorers as custom filters/metrics.

**Route B: keep the bespoke harness but bring it to standard.** Every run writes a manifest (`dataset_source`, `dataset_sha256`, `split`, `n`, `max_tokens`, `temperature`, `seed`, `no_think`, quantisation, provider, harness git sha, prompt template hash) plus `results/<model>/<benchmark>.jsonl` with one row per item (`prompt`, `raw_response`, `finish_reason`, `extracted`, `gold`, `score`, `usage`, `latency`). Add retries with backoff, concurrency, per-benchmark checkpointing, and a `status` per item of `scored` / `unparsed` / `error` / `truncated` — never collapse those into `0.0`.

Either way, three non-negotiables:

1. **A shared Uzbek text-normalisation helper** (NFC + apostrophe folding), applied to model output, gold strings, keywords, and references, before any comparison.
2. **Extraction failure is a first-class metric, not a wrong answer.** Report `unparsed_rate` per model per benchmark and suppress any cell above a published threshold.
3. **Golden regression tests**, seeded with exactly the strings that broke: `"To'g'ri javob: H"` → `H`; a `<think>`-wrapped response per benchmark; an unterminated `<think>`; `yo’q` with each apostrophe variant; a multi-line translation; an empty response asserting *unparsed*, not 0. Plus dataset validators as tests — they currently fail on 147/200 MMLU rows and 10 DTM rows. Then a CI workflow.

### 6.3 Leaderboard policy

Adopt, in order of value:

1. **Never average over differing subsets.** A model without a complete run gets per-benchmark cells and a suppressed aggregate — never a mean over what happens to be present.
2. **Normalise before aggregating**, HF Open LLM Leaderboard v2 style: `(raw − chance) / (1 − chance) × 100`, clamped at 0, computed per subtask. Chance is 0.25 for DTM, 0.1 for a 10-choice MMLU-Pro, 0 for generative tasks. Equal weight per benchmark, stated explicitly.
3. **Every cell ships `n` and a 95% Wilson interval.** Seven of the ten current MMLU intervals overlap. Rank is an interval too — show a rank spread and declare ties when spreads overlap.
4. **Pin a non-rankable "Random baseline" row** and badge any below-chance cell as a suspected extraction failure rather than a low score.
5. **Every row carries provenance**: harness commit, dataset version, quantisation/precision, chat template, temperature, seed, max tokens, run date, and an `ORGANISER-RUN` / `VERIFIED` / `SELF-REPORTED` badge.
6. **Versioned, dated changelog.** A harness change means a full re-run of every model — budget for that before changing anything.
7. **Publish per-sample outputs** for every run on public items. It is the strongest possible signal of confidence and it lets others find your bugs before your critics do.

### 7.2 The DTM copyright question — the highest-severity item in this report

The 2,066-item public release is already live on IEEE DataPort (DOI 10.21227/e4h4-kp42) and HuggingFace, extracted from **commercial 2019 exam-prep books**. The position, honestly stated:

- Individual MCQ items with crafted distractors are copyrightable literary works. The publisher additionally holds a compilation right in the selection and arrangement. DTM may hold rights of its own.
- Uzbekistan's Art. 8 "official documents" exemption almost certainly does **not** cover exam questions — they are not normative acts.
- Uzbekistan follows the civil-law model: a closed list of free-use exceptions bounded by the three-step test. **There is no fair-use defence**, and bulk extraction plus public redistribution of a question bank is not "quotation" or "illustration for teaching."
- VLM transcription creates no new rights — it is a reproduction, not a laundering step.

The field norm is to say nothing and rely on nobody suing (AGIEval disclaims data rights entirely; GAOKAO-Bench says nothing; KazMMLU chose CC BY-NC-SA and made only a scraping-policy compliance claim). **For a university lab publishing under its own name, in a jurisdiction where the rightsholder is a state agency you likely want a future relationship with, "everyone does it" is a weak position.**

What actually helps, ranked:

1. **A written permission letter** from DTM and from the exam-prep publisher, covering reproduction, translation, distribution and sublicensing — routed through the university's legal office, not signed by the team. This is the only thing that fully solves it.
2. **Commission original items** to the DTM 2019 blueprint. You then own the copyright, can validate keys with humans, and get a genuinely uncontaminated benchmark. Eliminates the entire legal section of the paper.
3. **A published takedown policy** with a named contact and a stated response window, plus a per-item provenance ledger (source ISBN, page, extraction date, model version, human reviewer) so selective removal is possible.
4. **Do not claim rights you don't have.** Use `license: other` with a file granting only the compilation, annotations and metadata under CC BY-SA, explicitly disclaiming ownership of the underlying items.

### 7.3 The paper

**LREC 2026 is the best fit**, with Data in Brief as fallback. Scientific Data is off the table (requires CC0/CC BY) and NeurIPS D&B treats gating as exceptional.

**The blocking gap is validation.** The draft says answer keys were "verified by an LLM-assisted pass (Claude Opus 4.6)." Every one of these venues will read that as a red flag, and Scientific Data would reject on it. Minimum remediation:

- Stratified random sample (n ≈ 385 for ±5% at 95% on the whole bank; n ≈ 100 per subject for per-subject estimates).
- **≥2 independent human annotators per sampled item**, blinded to the LLM's answer, with a written adjudication protocol.
- Report Cohen's/Fleiss' κ, human–LLM agreement, and an answer-key error rate with CI, per subject.
- Report VLM extraction fidelity separately (CER/WER vs human transcription) — extraction errors and key errors are different failure modes.
- Set `annotations_creators: machine-generated` on the card, and state the regime in Limitations.

Also correct in the draft: the "topics sampled uniformly within each subject" claim (false for tarix and fizika), the "uniform A/B/C/D" claim (state the actual distribution), the field-schema mismatch (`option_a` in the paper vs `option_A` in the CSV; `id`/`answer`/`test_number` in the JSON), and remove the 2 leaked items from the public CSV.

Add: `CITATION.cff`, a Zenodo version DOI per release, and a proper HF dataset card with the full template sections.
